\begin{frame}{Why tests are important}
\protect\phantomsection\label{why-tests-are-important}
\begin{itemize}
\tightlist
\item
  Risk Mitigation

  \begin{itemize}
  \tightlist
  \item
    Testing helps identify defects and failures early in the development
    process when they are less expensive to fix. This reduces project
    risks related to quality, security, performance, etc.
  \end{itemize}
\item
  Confidence

  \begin{itemize}
  \tightlist
  \item
    Executing a well–planned software test strategy provides confidence
    that the software works as intended before its release.
  \end{itemize}
\item
  Compliance

  \begin{itemize}
  \tightlist
  \item
    Testing can ensure that software adheres to standards, regulations,
    and compliance requirements. This is especially critical for
    safety–critical systems.
  \end{itemize}
\item
  User Satisfaction

  \begin{itemize}
  \tightlist
  \item
    Rigorous testing from a user perspective can verify usability,
    functionality, and compatibility. This increases customer/user
    satisfaction and reduces negative impacts to an organization’s
    reputation or finances from poor quality products.
  \end{itemize}
\end{itemize}
\end{frame}

\begin{frame}{Why tests are important}
\protect\phantomsection\label{why-tests-are-important-1}
\begin{itemize}
\tightlist
\item
  Optimization

  \begin{itemize}
  \tightlist
  \item
    Testing provides vital feedback that can be used to continuously
    improve software quality, user experience, security, performance and
    other product attributes.
  \end{itemize}
\item
  Cost Savings

  \begin{itemize}
  \tightlist
  \item
    Investing in testing activities reduces downstream costs related to
    defects found post–release. It is much cheaper to find and fix bugs
    earlier in the development cycle.
  \end{itemize}
\end{itemize}

… and many more reasons
\end{frame}

\begin{frame}{Why tests are important (SW developer perspective)}
\protect\phantomsection\label{why-tests-are-important-sw-developer-perspective}
\begin{itemize}
\tightlist
\item
  Enable us testing corner case scenarios

  \begin{itemize}
  \tightlist
  \item
    Testing enables us to validate that our code behaves correctly under
    various conditions, including edge cases.
  \end{itemize}
\item
  Ensure code stability

  \begin{itemize}
  \tightlist
  \item
    Testing helps maintain code stability by catching regressions and
    unintended side effects early in the development process.
  \end{itemize}
\item
  Facilitate refactoring and code maintenance

  \begin{itemize}
  \tightlist
  \item
    Testing allows developers to confidently refactor and maintain code,
    knowing that existing functionality is protected by a suite of
    automated tests.
  \end{itemize}
\end{itemize}
\end{frame}

\begin{frame}{Why tests are important (SW developer perspective)}
\protect\phantomsection\label{why-tests-are-important-sw-developer-perspective-1}
\begin{itemize}
\tightlist
\item
  They are instant!

  \begin{itemize}
  \tightlist
  \item
    Unit tests can be executed quickly (often in seconds or minutes),
    providing immediate feedback to developers about the correctness of
    their code.
  \end{itemize}
\item
  \textbf{Disclaimer}

  \begin{itemize}
  \tightlist
  \item
    They took time to write and maintain. Often it is 2x time of
    development. But AI can help significantly!
  \item
    Unit tests are not a silver bullet; they complement other testing
    types and practices to ensure overall software quality.
  \end{itemize}
\end{itemize}
\end{frame}

\begin{frame}{Different types of (automated) testing}
\protect\phantomsection\label{different-types-of-automated-testing}
\emph{Ordered from least complex to most complex}.
\end{frame}

\begin{frame}[fragile]{Different types of (automated) testing}
\protect\phantomsection\label{different-types-of-automated-testing-1}
\textbf{Unit tests}\\
\textbf{Written by:} Developers\\
\textbf{Target:} Classes\\
\textbf{Purpose:} Test individual units of code in isolation\\
\textbf{Complexity:} Low\\
\textbf{Example:} Test files that are part of repository,
i.e.~\texttt{EventHandlerTest.cpp}\\
Unit tests are very low level and close to the source of an application.
They consist in \textbf{testing individual methods and functions} of the
classes, components, or modules used by your software. Unit tests are
generally quite cheap to automate and can run very quickly by a
continuous integration server.
\end{frame}

\begin{frame}{Different types of (automated) testing}
\protect\phantomsection\label{different-types-of-automated-testing-2}
\textbf{Smoke testing}\\
\textbf{Written by:} Developers or QA engineers\\
\textbf{Target:} Application\\
\textbf{Purpose:} Check the basic functionality of an application\\
\textbf{Complexity:} Low\\
Smoke tests are basic tests that check the \textbf{basic functionality}
of an application. They are meant to be quick to execute, and their goal
is to give you the assurance that the major features of your system are
working as expected. Smoke tests can be useful right after a new build
is made to decide whether or not you can run more expensive tests, or
right after a deployment to make sure that they application is running
properly in the newly deployed environment.

\textbf{Fun fact:} Naming comes from hardware testing, where a “smoke
test” was a quick check to see if a device would power on without
emitting smoke.
\end{frame}

\begin{frame}{Different types of (automated) testing}
\protect\phantomsection\label{different-types-of-automated-testing-3}
\textbf{Fuzz testing}\\
\textbf{Written by:} Developers or QA engineers\\
\textbf{Target:} Application or Classes\\
\textbf{Purpose:} Identify security vulnerabilities and robustness
issues by providing invalid, unexpected, or random data as inputs\\
\textbf{Complexity:} Medium\\
Fuzz testing, or fuzzing, is a type of automated testing that involves
\textbf{providing invalid, unexpected, or random data as inputs} to a
computer program. The program is then monitored for crashes, memory
leaks, or other unexpected behaviors. Fuzz testing is particularly
useful for identifying security vulnerabilities and robustness issues in
software.
\end{frame}

\begin{frame}{Different types of (automated) testing}
\protect\phantomsection\label{different-types-of-automated-testing-4}
\textbf{Integration tests}\\
\textbf{Written by:} Developers\\
\textbf{Target:} Modules or services\\
\textbf{Purpose:} Test interactions between different modules or
services\\
\textbf{Complexity:} Medium\\
Integration tests verify that different \textbf{modules or services}
used by your application work well together. For example, it can be
testing the interaction with the database or making sure that
microservices work together as expected. These types of tests are more
expensive to run as they require multiple parts of the application to be
up and running.
\end{frame}

\begin{frame}{Different types of (automated) testing}
\protect\phantomsection\label{different-types-of-automated-testing-5}
\textbf{Functional tests}\\
\textbf{Written by:} Developers or QA engineers\\
\textbf{Target:} Application\\
\textbf{Purpose:} Test the application against business requirements\\
\textbf{Complexity:} Medium\\
Functional tests focus on the \textbf{business requirements} of an
application. They only verify the output of an action and do not check
the intermediate states of the system when performing that action. There
is sometimes a confusion between integration tests and functional tests
as they both require multiple components to interact with each other.
The difference is that an integration test may simply verify that you
can query the database while a functional test would expect to get a
specific value from the database as defined by the product requirements.
\end{frame}

\begin{frame}{Different types of (automated) testing}
\protect\phantomsection\label{different-types-of-automated-testing-6}
\textbf{End-to-end tests}\\
\textbf{Written by:} Developers or QA engineers\\
\textbf{Target:} Application\\
\textbf{Purpose:} Test the application from start to finish\\
\textbf{Complexity:} High\\
End-to-end testing replicates a \textbf{user behavior} with the software
in a complete application environment. It verifies that various user
flows work as expected and can be as simple as loading a web page or
logging in or much more complex scenarios verifying email notifications,
online payments, etc… End-to-end tests are very useful, but they’re
expensive to perform and can be hard to maintain when they’re automated.
It is recommended to have a few key end-to-end tests and rely more on
lower level types of testing (unit and integration tests) to be able to
quickly identify breaking changes.
\end{frame}

\begin{frame}{Different types of (automated) testing}
\protect\phantomsection\label{different-types-of-automated-testing-7}
\textbf{Acceptance testing}\\
\textbf{Written by:} Developers or QA engineers\\
\textbf{Target:} Application\\
\textbf{Purpose:} Verify if a system satisfies business requirements\\
\textbf{Complexity:} High\\
Acceptance tests are formal tests that verify if a system satisfies
\textbf{business requirements}. They require the entire application to
be running while testing and focus on replicating user behaviors. But
they can also go further and measure the performance of the system and
reject changes if certain goals are not met.
\end{frame}

\begin{frame}{Different types of (automated) testing}
\protect\phantomsection\label{different-types-of-automated-testing-8}
\textbf{Performance testing}\\
\textbf{Written by:} Developers or QA engineers\\
\textbf{Target:} Application\\
\textbf{Purpose:} Evaluate how a system performs under a particular
workload\\
\textbf{Complexity:} Medium\\
Performance tests evaluate how a system performs under a
\textbf{particular workload}. These tests help to measure the
reliability, speed, scalability, and responsiveness of an application.
For instance, a performance test can observe response times when
executing a high number of requests, or determine how a system behaves
with a significant amount of data. It can determine if an application
meets performance requirements, locate bottlenecks, measure stability
during peak traffic, and more.
\end{frame}
